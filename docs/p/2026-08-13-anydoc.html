How anydoc knows what a file really is before converting it to Markdown

2026-08-13 · firecrawl/anydoc · ★ 15001

What it is and why it's trending

anydoc is Firecrawl's Rust library for converting office documents — Word, PowerPoint, Excel, OpenDocument, RTF, EPUB, CSV, and text-based PDF — into GitHub-Flavored Markdown. It ships with Node.js, Python, and WebAssembly bindings, plus a CLI you can run with npx @firecrawl/anydoc report.docx. Nine days after launch it's at 15k stars, and the timing explains why: everyone building RAG pipelines or agents has hit the "user uploaded a .pptx" problem, and the existing answers are slow (LibreOffice headless: ~1.1s per document), narrow (mammoth does docx only), or both. anydoc's median conversion time is 4.4ms — no ML models, no subprocess, no external service. It also ships as an Agent Skill, so a coding agent can install it with one command and start reading office documents, which is exactly the distribution channel that gets a library trending in 2026.

How it actually works

The architecture is a funnel. Every format gets its own parser — there are separate frontends for the binary Office formats (.doc, .ppt, .xls), the OOXML packages (.docx, .pptx, .xlsx), ODF, RTF, and EPUB — but every parser emits the same intermediate document model: headings with anchors, nested lists with the source's own numbering, tables with merged cells, footnotes, even speaker notes. A single Markdown serializer then renders that model. That one design decision buys the property the README leads with: escaping, table syntax, and heading anchors come out identical whether the input was a .doc from 2003 or a .pptx from yesterday, and a serializer bug fixed once is fixed for all fourteen container variants. The lone exception is PDF, which routes through Firecrawl's pdf-inspector and emits Markdown directly, skipping the model.

Before any parsing happens, though, anydoc has to answer a question most converters punt on: what format is this file, really? It never trusts the extension first. Here's the top of src/formats/detect.rs:

pub(crate) fn from_bytes(bytes: &[u8]) -> Option<Format> {
    if bytes.starts_with(b"{\\rtf") {
        return Some(Format::Rtf);
    }
    if bytes.starts_with(&OLE_MAGIC) {
        return detect_ole(bytes);
    }
    if bytes.starts_with(b"PK\x03\x04") {
        return detect_zip(bytes);
    }
    if bytes[..bytes.len().min(1024)].windows(5).any(|w| w == b"%PDF-") {
        return Some(Format::Pdf);
    }
    None
}

RTF must open with a literal {\rtf group, so that's one comparison. The OLE magic number marks the 97–2003 binary formats; the ZIP local-file header marks everything modern, since docx, xlsx, pptx, ODF, and EPUB are all ZIP packages. The PDF check scans the first kilobyte rather than demanding %PDF- at byte zero, because the spec tolerates leading junk and real files have it.

The interesting detail: identity comes from the spec, not heuristics

Matching a container signature only tells you the wrapper, not the document, so detection has a second stage — and it's built entirely on what each specification designates as the format's identity, never on sniffing content. For OLE files, each binary Office spec mandates a stream name inside the compound file: WordDocument, PowerPoint Document, Workbook (or the older Book), compared case-insensitively because real producers write WORKBOOK. For ZIP packages there's a four-layer fallback chain:

  • The mimetype part, which ODF and EPUB require as the package's first entry.
  • For Microsoft's OPC packages, the package-level officeDocument relationship that names the main part, and that part's declared content type.
  • If content types are stale or generic — which happens in the wild — the main part's mandated XML root element (w:document, p:presentation, workbook) outranks them.
  • Last resort: conventional paths like word/document.xml or the binary xl/workbook.bin.

Each layer exists because some real-world producer violated the layer above it. The payoff: a spreadsheet renamed report.pdf still converts as Excel, an encrypted OOXML package is reported as encrypted rather than misparsed, and detection never errors — anything ambiguous returns None and falls back to the extension.

Who should use it

If you're ingesting user-uploaded documents into an LLM pipeline — RAG, agents, search indexing — this is now the obvious first thing to try, especially from Node or Python where the bindings stay off your hot path (conversion runs on the libuv thread pool; Python releases the GIL). The WASM build is a genuinely nice touch: the demo page converts files entirely in the browser, so nothing leaves the machine. The main gap is scanned PDFs — there's no OCR, image-only pages error as unsupported, and that's deliberately left to Firecrawl's hosted API. That's also the honest read on the project: it's the open-source engine of a commercial parsing product, with the benchmark harness in-repo but vendor-run. Even discounting for that, covering fourteen format variants at single-digit milliseconds with one consistent output is a real engineering result, not a wrapper.
