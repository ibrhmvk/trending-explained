How an agent-first CRM writes facts without guessing them

The CRM is where the agent keeps its notes

Comp AI's crm hit 8,300 stars in about two weeks by taking a swing at a category everyone claims to be reinventing. Their pitch: most CRMs are a database with a form in front of it, and the "AI CRMs" bolt a chat box onto the side of that form. Both still leave the actual work — finding out what is true about a contact and writing it down — to a human. This project inverts the relationship. The agent is not a feature of the CRM; the CRM is the agent's notebook. The agent is its own deployment (built on eve, Vercel's filesystem-first framework for durable agents), running on its own schedule against its own work queue, with a research budget it spends and then stops. Close the browser and it keeps going.

How it actually works

The monorepo is a Turborepo on Bun: a Next.js front end, a NestJS API that talks to the app over tRPC, Prisma on Postgres, and apps/agent as the interesting part. The agent has 18 tools (read_crm_history, identify_contact, record_fact, schedule_recheck…), four skills that are literally markdown prose versioned like code, and exactly one schedule: a dispatcher that decides nothing. It leases whatever is due from the agentTask table and starts a session per row. The whole work queue is one SQL statement in lib/tasks.ts:

UPDATE "agentTask" AS t
SET "leasedUntil" = ${until},
    "attempts" = t."attempts" + 1
FROM (
    SELECT t2.id FROM "agentTask" AS t2
    WHERE t2."finishedAt" IS NULL
        AND t2."dueAt" <= ${now}
        AND (t2."leasedUntil" IS NULL OR t2."leasedUntil" < ${now})
        AND t2."attempts" < ${MAX_ATTEMPTS}
    ORDER BY t2."priority" DESC, t2."dueAt" ASC
    LIMIT ${limit}
    FOR UPDATE SKIP LOCKED
) AS due
WHERE t.id = due.id

FOR UPDATE SKIP LOCKED is doing a lot of quiet work here: two dispatchers running concurrently skip each other's locked rows instead of blocking on them, so they take disjoint work with no coordinator. A run that crashes just lets its lease expire and the row becomes claimable again; a row that keeps failing hits MAX_ATTEMPTS and is retired. Anything that smells like "every N minutes, the ten oldest contacts" lives in a task's dueAt, not a cron expression — when the agent wants another look at someone in two weeks, it calls schedule_recheck and must state why, and that reason is shown to the sales rep.

Nothing about a person is guessed

The detail worth stealing is the evidence ledger. No tool accepts a confidence score, on the theory that a model asked to grade its own certainty will be wrong in the direction that makes it look useful. Instead, tools report what they observed, and lib/evidence.ts prices each kind of observation with a fixed weight:

  • profile.email-match — their email address is on the profile: 0.95
  • crm.thread-reply — they replied on a thread you have: 0.85
  • employer-only — employer matches, name does not: 0.2
  • contradiction — another source disagrees: 0

Arithmetic, not the model, decides the outcome: strong evidence writes to the record, weak evidence becomes a suggestion a human settles. The same paranoia shapes the sandbox. The agent gets a real shell — bash, grep, glob, a /workspace for keeping dossiers — but with deny-all egress, which costs nothing because web_fetch runs in the app runtime and web_search at the model provider. And the sandbox is never handed DATABASE_URL. A shell with credentials and network access is exfiltration-shaped even in an internal tool; a shell with neither is a text processor.

Who should use it

Small teams can genuinely self-host it: Bun, Docker Postgres, one .env, Google or Microsoft sign-in, and it runs with zero external API keys by mining your own threads and signature blocks — each key (Perplexity, LinkedIn via RapidAPI) just opens one more place to look. It is deliberately single-tenant; the maintainers argue an organizationId that always holds one value is a column, an index and a permissions check that buys nothing. But even if you never run it, it reads well as a reference architecture for durable agents: a Postgres lease queue, budgets, evidence-gated writes, and human-in-the-loop suggestions are patterns that transfer to any agentic system you're building.
